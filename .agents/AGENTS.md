# Custom Workspace Rules for Astro-E3ES & WordPress Headless Site

## 1. GUTENBERG BLOCK SERIALIZATION CONSTRAINTS
* **No Empty HTML wrappers in DB block markup**: Pure JavaScript blocks (like `e3es/video-embed`) that do not have active PHP `render_callback` implementations MUST have their complete rendered markup (including `iframe` elements) populated inside the database HTML (`post_content`). Saving empty wrappers (e.g. `<div class="db-video-wrapper"></div>`) is strictly forbidden because the frontend (Astro) REST API parser fetches from the public `content.rendered` output which strips out Gutenberg comments. If the HTML inside the database is empty, the video will not render.
* **Synchronized save() Validation**: When programmatically updating or seeding block HTML in the database, the saved outer tag, attributes, and classes MUST exactly match the output generated by the block's `save` function in `editor-blocks.js`. For example, `e3es/video-embed` expects `<section class="wp-block-e3es-video-embed db-video-section video-embed">` with matching properties. Mismatches will trigger Gutenberg block validation errors inside the WP dashboard, stripping custom components on next edit.

## 2. VIMEO PLAYER EMBED NORMALIZATION
* **Force Player URLs**: Always normalize vimeo link URLs to the player embed format (`https://player.vimeo.com/video/<id>?...`) inside both the frontend ASTRO parsers and backend Gutenberg blocks. Never save raw page URLs (`https://vimeo.com/<id>`) into `iframe` `src` fields, as Vimeo blocks frame requests via `X-Frame-Options` on non-player domains.
